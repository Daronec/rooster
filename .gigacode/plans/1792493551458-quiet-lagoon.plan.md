# План: Интеграция Cloud.ru как полного бэкенда для Rooster

## Описание

Интегрировать **Cloud.ru Object Storage** как бэкенд для Rooster, покрывая ВСЕ сущности: профиль, задачи, списки задач, планы, запасы материалов и команды. Использует Cloud.ru Serverless Functions (REST API) + Cloud.ru Object Storage (S3-compatible) для файлов.

**Важно**: Cloud.ru и Yandex Cloud — это разные платформы. Мы используем Cloud.ru (endpoint `storage.cloud.ru`).

**Архитектура**: Local-first Hive → SyncQueue → CloudRuSyncExecutor → Serverless Functions (REST API) + S3 (файлы)

**Новые зависимости не нужны** — существующий `dio: ^5.9.2` достаточен.

## Переменные окружения (ENV)

### 1. `.env` файл (Flutter assets)

Создать/обновить `.env` файл. Ключи загружаются через `flutter_dotenv` и доступны через `AppDotenv`.

| Ключ | Описание | Пример значения | Обязательный |
|------|----------|-----------------|--------------|
| `CLOUD_RU_SERVERLESS_ENDPOINT` | URL Yandex Serverless Functions для REST API | `https://serverless-function-id.serverless.yandexcloud.net` | **Да** |
| `CLOUD_RU_STORAGE_ENDPOINT` | URL Yandex Object Storage (S3-compatible) | `https://storage.cloud.ru` | **Да** |
| `CLOUD_RU_BUCKET_NAME` | Имя бакета для хранения файлов | `rooster-media` | **Да** |
| `CLOUD_RU_AVATARS_BUCKET` | Имя бакета для аватаров | `rooster-avatars` | Да |
| `CLOUD_RU_ACCESS_KEY` | IAM Access Key для S3 (только для бэкенда) | `YCAJEGrM3eK...` | Нет (S3 через presigned) |
| `CLOUD_RU_SECRET_KEY` | IAM Secret Key для S3 (только для бэкенда) | `YCAJeHx...` | Нет (S3 через presigned) |
| `VK_ID_CLIENT_ID` | VK ID Client ID (уже есть) | `...` | Да |
| `YANDEX_ID_CLIENT_ID` | Yandex ID Client ID (уже есть) | `...` | Да |

**Пример `.env` файла**:
```env
# Cloud.ru / Yandex Cloud
CLOUD_RU_SERVERLESS_ENDPOINT=https://serverless-function-id.serverless.yandexcloud.net
CLOUD_RU_STORAGE_ENDPOINT=https://storage.cloud.ru
CLOUD_RU_BUCKET_NAME=rooster-media
CLOUD_RU_AVATARS_BUCKET=rooster-avatars

# Auth (уже есть)
VK_ID_CLIENT_ID=your_vk_client_id
YANDEX_ID_CLIENT_ID=your_yandex_client_id
```

### 3. Как передаются ENV в приложение

1. **Runtime** (`.env`): Загружаются через `flutter_dotenv` в `loadAppDotEnv()` → доступны через `AppDotenv`
2. **Compile-time** (`Environment`): Передаются в `AppScopeRegister.createScope(env)` при инициализации
3. **CloudRuClient**: Получает `serverlessEndpoint` и `storageEndpoint` из `Environment` в `app_scope_register.dart`

### 4. Бэкенд (Cloud.ru Serverless Functions)

Для Serverless Functions переменные хранятся в настройках функции (не в клиенте):

| Переменная | Описание | Пример |
|-----------|----------|--------|
| `S3_ENDPOINT` | Endpoint Object Storage | `https://storage.cloud.ru` |
| `S3_BUCKET` | Имя бакета для файлов | `rooster-media` |
| `S3_AVATARS_BUCKET` | Имя бакета для аватаров | `rooster-avatars` |
| `S3_ACCESS_KEY` | IAM Access Key | `YCAJEGrM3eK...` |
| `S3_SECRET_KEY` | IAM Secret Key | `YCAJeHx...` |
| `DATABASE_URL` | PostgreSQL connection string | `postgresql://user:pass@...` |

**Важно**: Секреты (S3 keys, DATABASE_URL) хранятся ТОЛЬКО на бэкенде, НЕ в клиенте. S3-загрузки из Flutter идут через presigned URLs, сгенерированные сервером.

### 5. Получение ключей доступа Cloud.ru

#### IAM Access Key (для S3 и Serverless Functions)

1. Войти в [Cloud.ru Control Panel](https://mc.cloud.ru/)
2. Перейти в **IAM** → **Пользователи** → выбрать пользователя → **Ключи доступа**
3. Нажать **Создать ключ**
4. Сохранить `access_key` и `secret_key`

📖 **Документация**: [Создание IAM ключа доступа](https://developers.cloud.ru/docs/iam/operations/api-key/create.html)

#### Object Storage Bucket

1. Перейти в **Object Storage** → **Бакеты** → **Создать бакет**
2. Указать имя (`rooster-media`, `rooster-avatars`)
3. Выбрать регион (`ru-1` — Москва)
4. ACL: **Private**

📖 **Документация**: [Создание бакета Object Storage](https://developers.cloud.ru/docs/object-storage/operations/bucket/create.html)

#### Сервисный аккаунт с правами на S3

1. Создать сервисный аккаунт: **IAM** → **Сервисные аккаунты** → **Создать**
2. Назначить роль: **storage.admin** или кастомную с правами `storage.objects.get`, `storage.objects.put`, `storage.objects.create`
3. Привязать SA к Serverless Functions в настройках функции

📖 **Документация**: [Создание сервисного аккаунта](https://developers.cloud.ru/docs/iam/operations/service-account/create)
📖 **Документация**: [Назначение ролей](https://developers.cloud.ru/docs/access-management/operations/role/assign)

#### Endpoint Object Storage

| Регион | Endpoint |
|--------|----------|
| ru-1 (Москва) | `https://storage.cloud.ru` |

📖 **Документация**: [Endpoints Object Storage](https://developers.cloud.ru/docs/object-storage/s3/endpoints.html)

## Фаза 3: Синхронизация задач и списков

### Шаг 3.1: Реализовать CloudRuSyncExecutor

**Файл**: `lib/features/cloud_ru/sync/cloud_ru_sync_executor.dart` (ЗАМЕНИТЬ существующий stub)

Центральный оркестратор для push-pull синхронизации:

```
1. PUSH: Обработка outbound SyncOperations из очереди → Serverless Functions
2. PULL: Загрузка всех удалённых сущностей из Serverless Functions
3. MERGE: Применение удалённых сущностей к локальному Hive через merge policies
4. CLEAN: Удаление обработанных операций из очереди
```

**Конструктор**: Получает `CloudRuClient`, `ISyncQueue` и интерфейсы репозиториев через DI:
- `ITasksRepository` — для слияния изменений задач
- `ITaskListsRepository` — для слияния изменений списков
- `IPlanningRepository` — для слияния изменений планов
- `IMaterialStockRepository` — для слияния изменений материалов

**Фаза PUSH** (outbound → cloud):
- Загрузить все `SyncOperation` из очереди
- Сгруппировать по типу (`upsertTask`, `deleteTask`, и т.д.)
- Batch upsert через `/tasks/sync`, `/task-lists/sync`, `/plans/sync`
- Индивидуальные удаления через DELETE эндпоинты
- Логирование ошибок для повторных попыток

**Фаза PULL** (cloud → local):
- Загрузить ВСЕ удалённые сущности: `GET /tasks`, `GET /task-lists`, `GET /plans`, `GET /material-stock`
- Для каждой сущности применить merge policy:
  - **Задачи**: `TaskRemoteMergePolicy` — сравнение `updatedAtMillis`
  - **Списки**: `TaskListRemoteMergePolicy` — сравнение `updatedAtMillis`
  - **Планы**: `PlanRemoteMergePolicy` — сравнение `contentRevision`
  - **Материалы**: `MaterialStockRemoteMergePolicy` — полная замена
- Записать слитые сущности в Hive через методы репозиториев
- Логирование конфликтов слияния

**Фаза CLEAN**:
- Удалить успешно обработанные операции из очереди
- Сохранить неудачные операции для повт��рной попытки (существующий backoff обрабатывает это)

**Проверка**: Unit-тесты для логики push/pull/merge.

## Фаза 6: Backend Serverless Functions

### Шаг 6.1: Развернуть Serverless Functions

**Необходимые эндпоинты** (Yandex Cloud Serverless Functions):

| Функция | Триггер | Эндпоинт | Назначение |
|---------|---------|----------|------------|
| `tasksApi` | HTTP | `/tasks`, `/tasks/:id`, `/tasks/sync` | CRUD задач + batch sync |
| `taskListsApi` | HTTP | `/task-lists`, `/task-lists/:id`, `/task-lists/sync` | CRUD списков + batch sync |
| `plansApi` | HTTP | `/plans`, `/plans/:id`, `/plans/sync` | CRUD планов + batch sync |
| `materialStockApi` | HTTP | `/material-stock` | GET/PUT запасов материалов |
| `profileApi` | HTTP | `/profile` | GET/PUT профиля |
| `teamsApi` | HTTP | `/teams`, `/teams/:id`, `/teams/invite`, `/teams/leave` | CRUD команд |
| `storageApi` | HTTP | `/storage/presigned-upload`, `/storage/presigned-download` | Presigned URL для S3 |

**Реализация бэкенда** (для разработчика Yandex Cloud):
- Использовать PostgreSQL для постоянного хранения
- Таблица каждой сущности: `id`, `user_id`, JSONB payload, `updated_at`, `content_revision` (для планов)

3. Изменить задачу локально → выйти в онлайн → убедиться в обновлении сервера
4. Удалить задачу локально → выйти в онлайн → убедиться в удалении с сервера

### Шаг 7.2: Переход Offline → Online

Сценарии тестирования:
1. Создать 5 задач офлайн → выйти в онлайн → убедиться, что все 5 синхронизировались

3. Загрузить профиль на новом устройстве → убедиться, что профиль + аватар загрузились

Сценарии тестирования:
