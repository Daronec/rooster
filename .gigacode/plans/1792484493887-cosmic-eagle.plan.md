## Задача 2: SRP — TasksRepositoryImpl является God Class

**Серьёзность:** 🔴 Критическое
**Объём:** ~200 строк, 7 обязанностей в saveTask

### Текущая структура

```
TasksRepositoryImpl (~200 строк)
├── Hive storage (CRUD)          ← _box.put(), _box.delete(), _loadTaskById()
├── Sync queue management        ← _syncQueue.enqueue()
├── Analytics logging            ← _analytics.logCreateTask(), logCompleteTask()
├── Due reminder management      ← _dueReminderGateway.upsertDueReminder()
├── Task change history          ← _taskChangeHistoryWriter.addChange()
├── Image upload enqueue         ← task_image_upload_enqueue.enqueueTaskImageUploadIfNeeded()
└── Schedule sync                ← _syncManagerRef.scheduleSync()
```

### Проблема

Метод `saveTask` выполняет 7 обязанностей одновременно. При изменении любой из них (например, добавить новую метрику аналитики) нужно лезть в один большой метод, рискуя задеть другие обязанности.

### Анализ зависимостей

| Зависимость | Тип | Обязательность |
|-------------|-----|----------------|
| Box<dynamic> _box | Hive box | Required |
| ISyncQueue _syncQueue | Очередь синка | Required |
| SyncManagerRef _syncManagerRef | Триггер синка | Required |
| Uuid _uuid | Генератор ID | Required |
| IAppAnalyticsGateway? _analytics | Метрики | Optional (nullable) |
| ITaskDueReminderGateway? _dueReminderGateway | Напоминания | Optional (nullable) |
| ITaskChangeHistoryWriter? _taskChangeHistoryWriter | История | Optional (nullable) |
| ITaskChangeAuthorProvider? _taskChangeAuthorProvider | Автор | Optional (nullable) |

### Рекомендуемое решение

**Стратегия:** Выделить обязанности в отдельные сервисы данных с последующим рефакторингом `saveTask`.

#### Шаг 1: Создать `ITaskPersistenceService`

```dart
// lib/features/tasks/data/services/i_task_persistence_service.dart
abstract interface class ITaskPersistenceService {
  Future<void> saveTaskLocally(TaskEntity task);
  Future<void> deleteTaskLocally(String taskId);
  Future<TaskEntity?> loadTask(String taskId);
  Future<void> mergeRemoteTaskIfNewer(TaskEntity remote);
  Future<void> markTaskSyncedAfterRemotePush(String taskId);
}
```

**Обязанности:** Только Hive + SyncQueue (CRUD + постановка в очередь).

#### Шаг 2: Создать `ITaskLifecycleService`

```dart
// lib/features/tasks/data/services/i_task_lifecycle_service.dart
abstract interface class ITaskLifecycleService {
  Future<void> onTaskCreated(TaskEntity task);
  Future<void> onTaskUpdated(TaskEntity task, TaskEntity previous);
  Future<void> onTaskDeleted(TaskEntity task);
}
```

**Обязанности:** Analytics + Reminders + ChangeHistory + ImageUpload + ScheduleSync.

#### Шаг 3: Реализовать сервисы

```dart
// lib/features/tasks/data/services/task_persistence_service.dart
final class TaskPersistenceService implements ITaskPersistenceService {
  TaskPersistenceService({
    required Box<dynamic> tasksBox,
    required ISyncQueue syncQueue,
    required SyncManagerRef syncManagerRef,
    required Uuid uuid,
  }) : /* ... */;
}

// lib/features/tasks/data/services/task_lifecycle_service.dart
final class TaskLifecycleService implements ITaskLifecycleService {
  TaskLifecycleService({
    IAppAnalyticsGateway? analytics,
    ITaskDueReminderGateway? dueReminderGateway,
    ITaskChangeHistoryWriter? taskChangeHistoryWriter,
    ITaskChangeAuthorProvider? taskChangeAuthorProvider,
    required SyncManagerRef syncManagerRef,
    required Uuid uuid,
    // ... image upload gateway
  });
}
```

#### Шаг 4: Рефакторинг TasksRepositoryImpl

```dart
final class TasksRepositoryImpl implements ITasksRepository {
  TasksRepositoryImpl({
    required ITaskPersistenceService persistence,
    required ITaskLifecycleService lifecycle,
  }) : _persistence = persistence, _lifecycle = lifecycle;

  @override
  Future<void> saveTask(TaskEntity task) async {
    final existing = await _persistence.loadTask(task.id);
    await _persistence.saveTaskLocally(task);
    await _lifecycle.onTaskUpdated(task, existing);
  }

  @override
  Future<void> deleteTask(String taskId) async {
    final existing = await _persistence.loadTask(taskId);
    await _persistence.deleteTaskLocally(taskId);
    if (existing != null) {
      await _lifecycle.onTaskDeleted(existing);
    }
  }
}
```

### Оценка сложности

| Параметр | Значение |
|----------|----------|
| Новых файлов | 4 (2 интерфейса + 2 реализации) |
| Изменений в TasksRepositoryImpl | ~60 строк → ~30 строк |
| Изменений в AppScopeRegister | +4 новых сервиса в DI |
| Риск регрессии | Средний (изменить логику save/delete) |
| Тесты | Нужно добавить unit-тесты для сервисов |

### Альтернатива (минимальный риск)

Если полный рефакторинг слишком рискован — вынести только **один** сервис:

```dart
// Только analytics + reminders (наиболее изолированные)
final class TaskNotificationService {
  Future<void> upsertReminder(TaskEntity task);
  Future<void> cancelReminder(String taskId);
  Future<void> logTaskAnalytics(TaskEntity task, bool wasExisting);
}
```

Это уменьшит `saveTask` с 7 обязанностей до 5, не затрагивая Hive/sync-логику.

## Задача 5: Отсутствие DTO для API бизнес-данных

**Серьёзность:** 🟡 Среднее
**Контекст:** API-слой использует raw `Map<String, dynamic>`, Retrofit не используется

### Текущее состояние API-слоя

```
lib/api/
  ├── app_dio_configurator.dart    # Dio client factory
  ├── data/
  │   ├── app_update_dto.dart      # ✅ Infrastructure DTO
  │   ├── constants_dto.dart       # ✅ Infrastructure DTO
  │   ├── device_information_dto.dart # ✅ Infrastructure DTO
  │   ├── error_dto.dart          # ✅ Infrastructure DTO
  │   └── info_errors_dto.dart    # ✅ Infrastructure DTO
  └── utils/
      └── dto_utils.dart           # Safe JSON reading

lib/features/cloud_ru/api/
  └── cloud_ru_client.dart         # Hand-written Dio client
```

### Как сейчас передаются бизнес-данные

```dart
// CloudRuClient — ВСЕ методы используют raw Maps
Future<List<Map<String, dynamic>>> fetchTasks() async { ... }
Future<void> syncTasks(List<Map<String, dynamic>> tasks) async { ... }
Future<Map<String, dynamic>> fetchProfile() async { ... }
```

### Бизнес-объекты без DTO

| Entity | Полей | Приоритет DTO |
|--------|-------|---------------|
| TaskEntity | 30+ | 🔴 Высокий (основной объект) |
| TaskListEntity | 4 | 🟡 Средний |
| PlanningPlanEntity | 6 | 🟡 Средний |
| ProfileEntity | 3 | 🟢 Низкий |
| BudgetPeriodEntity | 5 | 🟢 Низкий |
| MaterialStockItemEntity | 4 | 🟢 Низкий |

### Почему DTO пока не критично

1. **Offline-first архитектура:** Основной поток данных — Hive → Domain, не API
2. **Sync executor — stub:** `CloudRuSyncExecutor.executeOutboundSync()` помечен как `TODO(cloud.ru)`, реальная интеграция не начата
3. **NoopSyncRemoteExecutor:** Сейчас sync-операции не отправляются на сервер (возвращают `Result.ok(null)`)
4. **Retrofit не используется:** В `pubspec.yaml` есть `retrofit_generator`, но ни одного `@RestApi` интерфейса нет

### Когда DTO станет критичным

- При подключении реального бэкенда (cloud.ru / Appwrite REST API)
- При необходимости валидации входящих данных от сервера
- При необходимости type-safe маппинга API → Domain

### Рекомендуемый подход (когда начнётся API интеграция)

1. **Создать DTO-классы** в `lib/features/tasks/data/dto/`
2. **Использовать json_serializable** (уже есть в проекте)
3. **Создать mappers** `TaskDto → TaskEntity` в `lib/features/tasks/data/mappers/`
4. **Рассмотреть Retrofit** для type-safe API клиента

### Оценка сложности

| Параметр | Значение |
|----------|----------|
| Новых файлов (TaskDto) | 1 DTO + 1 mapper |
| Изменений в CloudRuClient | Значительные (все методы) |
| Риск регрессии | Высокий (изменить контракт API) |
| Блокирующий фактор | Нет (API интеграция ещё не начата) |

### Рекомендация

**Отложить** до начала реальной API-интеграции. Сейчас это premature optimization — бизнес-данные циркулируют через Hive, а не через API.

## Задача 7: Naming — TaskEntityCodec vs Mapper Pattern

**Серьёзность:** 🟢 Низкое
**Контекст:** Все 7 codec-классов используют static методы, архитектурный навык предписывает *Mapper

### Текущие codec-классы

| Файл | Класс | Методы | Schema Version |
|------|-------|--------|----------------|
| task_entity_codec.dart | TaskEntityCodec | static toMap/fromMap | v9 |
| task_list_entity_codec.dart | TaskListEntityCodec | static toMap/fromMap | - |
| task_change_entity_codec.dart | TaskChangeEntityCodec | static toMap/fromMap | - |
| budget_period_codec.dart | BudgetPeriodCodec | static toMap/fromMap | v1 |
| material_stock_item_codec.dart | MaterialStockItemCodec | static toMap/fromMap | v1 |
| material_stock_snapshot_codec.dart | MaterialStockSnapshotCodec | static toMap/fromMap | - |
| planning_plan_entity_codec.dart | PlanningPlanEntityCodec | static toMap/fromMap | - |

### Паттерн реализации

```dart
final class TaskEntityCodec {
  const TaskEntityCodec._();  // private constructor (sealed)
  static const int currentSchemaVersion = 9;

  static Map<String, Object?> toMap(TaskEntity entity) { ... }
  static TaskEntity fromMap(Map<String, dynamic> map) { ... }

  // Private static helpers
  static String? _readNullableString(Object? raw) { ... }
}
```

### Архитектурный конфликт

**Навык (data layer):**
> "Используй ConverterToAndFrom для DTO-to-Entity преобразования"

**Реальность:**
> Codec-классы используются для Hive-сериализации (Entity ↔ Map), а не для DTO-маппинга

### Почему *Codec — допустимый паттерн для Hive

1. **Hive требует статических методов** для адаптеров (если используются HiveAdapter)
2. **В проекте нет HiveAdapter** — данные хранятся как raw Maps, codec только сериализует
3. **Все 7 codec-классов** единообразно используют static pattern
4. **ConverterToAndFrom** используется только для DTO-маппинга (отдельный паттерн)

### Рекомендация

**Не рефакторить**, а **документировать** паттерн:

```markdown
## Hive Codec Pattern

Все codec-классы (`*Codec`) в проекте используют static методы для сериализации
сущностей в/из Hive Maps. Это допустимый паттерн, потому что:

1. Hive хранит данные как raw Maps, не требует HiveAdapter
2. Codec — это сериализатор, не маппер между слоями
3. ConverterToAndFrom используется только для DTO-to-Entity маппинга

### Правила
- Все codec-классы — `final class` с private constructor `ClassName._()`
- Методы — `static Map<String, Object?> toMap(Entity)` и `static Entity fromMap(Map)`
- Private helpers — `_` prefix
- Некоторые codec имеют `currentSchemaVersion` для миграций
```

| Параметр | Значение |
|----------|----------|
| Новых файлов | 0 |
| Изменений в коде | 0 (только документация) |
| Риск регрессии | Нулевой |
| Ценность | Низкая (конвенция уже единообразна) |
