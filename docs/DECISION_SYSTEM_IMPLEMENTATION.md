# Детальная реализация: система принятия решений

Исходная концепция: [DECISION_SYSTEM_PLAN.md](./DECISION_SYSTEM_PLAN.md).

Ниже — поэтапный план внедрения в кодовую базу **Rooster** с учётом Clean Architecture, существующей фичи `tasks` (Hive, `TaskEntity`, репозитории, синк-очередь) и правил слоёв из `.cursor/rules`.

---

## 0. Цели и ограничения

**Цели**

- Задача описывается полями, достаточными для расчёта **выполнимости** и **приоритета «сейчас»**.
- Пользователь видит не только список, а **объяснение**, почему задача недоступна, и **топ кандидатов** на сегодня.
- Зависимости между задачами блокируют появление в «готовых» до закрытия предшественников.

**Ограничения проекта**

- Домен не импортирует Flutter/UI/Hive.
- Логика скоринга и статусов — **чистые функции / сервисы в domain**, зависимости через абстракции (порты), если нужны данные извне (бюджет, склад).
- Хранение — как сейчас, **Hive** в data-слое; миграции полей через версию схемы/кодека или отдельные ключи боксов.
- Локализация всех новых строк UI — `assets/flutter_i18n` + генерация при принятом в проекте процессе.

## 1. Доменная модель

### 1.1. Расширение задачи

Сейчас: `TaskEntity` (список, срок, приоритет, статус выполнения, синк и т.д.) — см. `lib/features/tasks/domain/entities/task_entity.dart`.

**Добавить** (имена ориентировочные, финально согласовать с неймингом проекта):

| Поле / концепция | Тип | Назначение |
ость |
| `complexity` | `int` (1–5) | усилие / длительность |
| `estimatedCost` | `double` | оценка в деньгах (валюта UI отдельно) |
| `materialRequirementIds` | `List<String>` | ссылки на позиции склада (не сырые строки в бизнес-логике, если вводите справочник) |
| `dependencyTaskIds` | `List<String>` | id задач-предшественников |
| `decisionStatus` | enum **или** вычисляемое значение | см. п. 1.2 |

**Совместимость**

- Существующий `TaskStatusEntity` (pending / completed) остаётся про **факт выполнения** задачи пользователем.
- Новый контур «решений» (`ready`, `blocked_*`) — про **доступность к работе сейчас**. Варианты:
  - **A (рекомендуется):** отдельный enum `TaskFeasibilityStatus` + опционально кэш в entity для отображения без пересчёта.
  - **B:** не хранить статус, считать на лету в use case (проще миграция, больше CPU при больших списках).

**Дедлайн**

- Уже есть `dueAt`; при необходимости связать **срочность** с дедлайном правилом в политике (например, если `dueAt` близко — поднять эффективную urgency), не дублируя лишний `deadline`, если не нужен отдельно от `dueAt`.

### 1.2. Enum статусов выполнимости (из плана)

Файл вида `lib/features/tasks/domain/entities/task_feasibility_status_entity.dart` (или `..._enum.dart` по конвенции проекта):

- `blockedMoney`
- `blockedMaterials`
- `blockedDependencies`
- `ready`
- `inProgress` — опционально: может совпадать с тем, что задача «взята в работу» в UI; иначе маппить из `TaskStatusEntity` + флага.
- `done` — обычно выводится из `TaskStatusEntity.completed`, чтобы не рассинхронизировать два «done».

### 1.3. Зависимости

- Граф **направленный**: ребро «задача A зависит от B» хранится как `A.dependencyTaskIds` содержит `B.id`.
- В domain: функция проверки **циклов** при сохранении (запрет циклических зависимостей) — отдельный небольшой модуль `TaskDependencyValidator` (SRP).
- «B готово» = для домена: `TaskStatusEntity.completed` у B (и при необходимости доп. условия, если появятся подзадачи).

### 1.4. Ресурсы: бюджет и склад

**Новые сущности (domain)**

- `BudgetPeriodEntity` — например, месяц: `year`, `month`, `amountLimit`, `amountSpent` (или только лимит, траты считать из задач — решение на этапе проектирования).
- `MaterialStockItemEntity` — `id`, `name`, `quantity`, `unit` (опционально), при необходимости `tags` для сопоставления с `materialRequirementIds`.

**Порты (интерфейсы в domain)**

- `IBudgetRepository` / `IMaterialStockRepository` — чтение-запись периода и позиций склада.
- Реализации в `data`: Hive-боксы + кодеки/мапперы, без импорта `Widget`.

## 2. Движок решений (domain)

### 2.1. Входные данные для расчёта

Структура контекста (не обязательно один класс, но удобно):

- текущая задача;
- `Map<String, TaskEntity>` или ленивый резолвер id → задача (для зависимостей);
- активный бюджетный период;
- список складских позиций;
- правила (коэффициенты формулы).

### 2.2. Формула Feasibility Score (из плана)

Зафиксировать в коде как **версия 1** с именованными константами (без магических чисел в теле формулы):

```text
base = importance * wI + urgency * wU
penaltyComplexity = complexity * wC
penaltyCost = f(estimatedCost, budgetRemaining, budgetCoefficient)
bonusMaterials = g(materialsSatisfied)
penaltyDependencies = h(unresolvedDependencyCount)
score = base - penaltyComplexity - penaltyCost + bonusMaterials - penaltyDependencies
```

- `f`, `g`, `h` — маленькие чистые функции или стратегии (OCP: смена политики без правки всего use case).
- Границы: например, `score` ограничить диапазоном, чтобы UI стабильно сортировал.

**Юнит-тесты** (обязательно): таблица кейсов из плана (септик vs траншея) + границы 1–5, отсутствие бюджета, пустые зависимости.

### 2.3. Определение `TaskFeasibilityStatus`

Чистая функция `resolveFeasibilityStatus(...)` **в порядке приоритета блокировок** (пример):

1. Если задача уже `completed` → `done` (или не показывать в decision-режимах).
2. Если есть незавершённые зависимости → `blockedDependencies` (+ список id/заголовков для UI через отдельный DTO/результат use case).
3. Если не хватает денег по правилу бюджета → `blockedMoney` (+ число нехватки).
4. Если не хватает материалов → `blockedMaterials` (+ список недостающих).
5. Иначе → `ready`.

`inProgress` — либо отдельный флаг в задаче, либо синоним «не completed, но пользователь отметил старт»; зафиксировать одно правило в документе после UX-ревью.

### 2.4. Use cases (публичные сценарии)

Рекомендуемые классы (имена примерные):

| Use case | Ответственность |
|----------|-----------------|
| `CalculateTaskFeasibility` | score + статус + **причины** (структурированно) для одной задачи |
| `ListTodayReadyTasks` | фильтр `ready`, сортировка по score, лимит N (например 3) |
| `ListBlockedTasksWithReasons` | все не-done с статусом ≠ ready, сортировка по «силе блокировки» или по score |
| `ValidateTaskDependencies` | циклы, несуществующие id, self-dependency |
| `SuggestTaskSplit` | эвристика: если complexity и cost выше порога — вернуть текстовые/структурные подсказки (MVP: один экран с рекомендацией без авто-разбиения) |

Зависимости use case только от **репозиториев и чистых калькуляторов** — не от `BuildContext`.

## 3. Слой данных (Hive)

### 3.1. Миграция `TaskEntity`

- Расширить сериализацию в `TaskEntityCodec` (или аналог): новые поля с **значениями по умолчанию** для старых записей (`importance = 3`, пустые списки, `estimatedCost = 0`).
- Версия схемы: либо поле `schemaVersion` в map, либо отдельный ключ в боксе — как принято в проекте для задач.

### 3.2. Новые боксы / ключи

- `budget_periods` — список/мапа периодов.
- `material_stock` — склады.

Количество боксов держать разумным; при росте данных рассмотреть один бокс с префиксами ключей.

### 3.3. Репозитории

- Расширить `ITasksRepository` **осторожно**: не раздувать интерфейс; для склад/бюджета — отдельные порты (ISP).
- Реализации в `tasks/data/repositories/…` с тем же паттерном, что существующие задачи (watch, save, enqueue sync если нужно).

**Синхронизация**

- Решить, уходят ли бюджет/склад в облако в текущей стратегии (Appwrite-only / offline). На MVP — только локально, без записи в sync queue.

**Реализация в коде (MVP, D2-08)**

- Hive-бокс `task_decision_v1` (`TaskDecisionHiveStorageConstants`): ключ `budget_active` — одна map активного [BudgetPeriodEntity]; ключ `material_stock_items` — список map [MaterialStockItemEntity].
- `BudgetRepositoryImpl` и `MaterialStockRepositoryImpl` **не** ставят операции в `ISyncQueue` и не вызывают облачный sync; данные только на устройстве. Задачи по-прежнему в `tasks_v1` с полями решений и `schemaVersion` в map задачи.

**Регрессия списка задач (D2-07)**

- Автоматически: `task_entity_codec_migration_test`, `budget_material_repositories_hive_test`, use case-тесты «Сегодня» / «Заблокировано».
- Ручная проверка: после обновления открыть экран «Задачи», убедиться что список и группы работают; в release панель «Решения» скрыта, в debug — свёрнутая карточка превью.

## 4. Слой представления (Flutter)

### 4.1. Три режима UI (из плана)

Варианты интеграции с текущей навигацией (`auto_route`):

- **Вкладки** внутри существующего экрана задач или отдельный пункт меню «Решения».
- Три подмаршрута: `Today`, `Blocked`, `Resources`.

**Экран «Сегодня»**

- Верх: заголовок + краткая сводка (сколько ready).
- Список: до 3 карточек (план UX), далее «Показать ещё».
- Каждая карточка: title, score (опционально скрыт настройкой), ключевые метки (срок, стоимость).

**Экран «Заблокировано»**

- Группировка по `TaskFeasibilityStatus` или единый список с бейджем причины.
- Развёрнутая строка: человекочитаемое объяснение из результата use case (локализованные шаблоны с плейсхолдерами).

**Экран «Ресурсы»**

- Форма/список бюджета на период.
- Список материалов + быстрое редактирование количества.
- Не смешивать с инфраструктурными интеграциями — отдельная фича или подфича `tasks` по границам команды.

### 4.2. WidgetModel / Elementary

- Один WM на экран или общая модель + три лёгких виджета — по сложности; не нарушать SRP.
- Загрузка через model → use case → repository (как в остальных фичах).

### 4.3. Локализация

- Ключи вида `tasks.decision.todayTitle`, `tasks.decision.blockedReason.money`, `tasks.decision.blockedReason.materials`, …
- Все языки проекта + прогон генератора i18n по принятому в репо процессу.

## 6. «Разбить задачу» (MVP → v2)

**MVP**

- Кнопка «Сложная задача» → экран/диалог с текстовыми рекомендациями (шаблоны по порогам complexity/cost).
- Опционально: создать подзадачи вручную (если в домене появятся подзадачи) — отложить, если нет модели parent/child.

**v2**

- Мастер разбиения: создаёт N черновиков задач с зависимостями цепочкой и уменьшенными cost/complexity.

## 9. Порядок внедрения (фазы)

### Фаза 1 — Домен + тесты (без UI)

1. Enum `TaskFeasibilityStatus` + value object для «причины блокировки».

6. Миграция задач в кодеке.
7. Реализации репозиториев.

### Фаза 3 — Use cases списков

8. `ListTodayReadyTasks`, `ListBlockedTasksWithReasons`.
9. Связка с существующим списком задач (не ломать текущий UX).

### Фаза 4 — UI

10. Три экрана + маршруты + WM + локализация.

## 10. Риски и решения

| Риск | Митигация |
|------|-----------|
| Раздувание `TaskEntity` | Выделить вложенный value object `TaskDecisionProfile` в том же слое domain, один импорт в кодеке |
| Дублирование «статус выполнения» и «статус выполнимости» | Чёткое именование и документация; UI показывает оба там, где нужно |
| Производительность на больших графах | Кэшировать score на запись задачи или инвалидировать точечно; измерить до оптимизации |
| i18n склонения | Использовать параметризованные строки; избегать конкатенации в WM |
