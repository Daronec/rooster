# План: двухстратегийная авторизация (Firebase+GMS и Huawei)

## Цель

Выбрать **одну из двух стратегий** входа и работы с облаком в зависимости от возможностей устройства:

| Условие                                                                              | Стратегия                                                                                     |
|--------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------|
| Доступны **Firebase** (инициализация успешна) **и** **Google Mobile Services (GMS)** | **Firebase-стратегия** — стандартные SDK Firebase (Auth, Functions, Firestore и т.д.)         |
| Firebase **или** GMS **недоступны**, при этом устройство **Huawei с HMS**            | **Huawei-стратегия** — Account Kit (HUAWEI ID), обход ограничений GMS там, где это необходимо |

Стратегия должна определяться **явно** на старте приложения (или при смене окружения), без размазывания `if` по UI.

---

## Текущее состояние проекта (точка отсчёта)

- Уже есть: вход Google, Apple (iOS), анонимный Firebase, HUAWEI ID через HMS + обмен `id_token` на Firebase **custom token** через Cloud Function (`signInWithHuawei`), HTTP-fallback вызова callable на устройствах без GMS.
- Проблема продукта: на Huawei **без GMS** часть Firebase-клиента (например, нативный `cloud_functions`) ведёт себя нестабильно; часть сервисов завязана на GMS.

План ниже **формализует** разделение на две ветки и доводит до консистентной архитектуры.

## 1. Определение стратегии (детекция)

### 1.1. Сигналы

1. **`firebaseAvailable`** — результат `Firebase.initializeApp` (уже принят в проекте).
2. **`gmsAvailable`** (Android) — наличие рабочих Google Play services (не только «пакет установлен»): например проверка через `GoogleApiAvailability` или эквивалент; для Flutter — тонкий порт в data-слой + реализация под Android.
3. **`isHuaweiHmsDevice`** (Android) — эвристика: производитель / марка, наличие `com.huawei.hwid`, или `HmsApiAvailability`; цель — не путать «просто Android без GMS» с «Huawei + HMS».

### 1.2. Правило выбора

```
если firebaseAvailable && gmsAvailable
  → стратегия Firebase
иначе если Platform.isAndroid && isHuaweiHmsDevice && hmsCoreUsable
  → стратегия Huawei
иначе
  → ограниченный режим (только локально / офлайн / сообщение пользователю)
```

Уточнения:

- **iOS / desktop**: при отсутствии GMS на Android правило не применяется; там остаётся Firebase (и Apple на iOS).
- **`hmsCoreUsable`**: HMS Core установлен и версия достаточна для Account Kit (как сейчас в сценарии HUAWEI ID).

### 1.3. Где хранить решение

- **Domain**: enum `AuthBackendStrategy { firebase, huawei, offlineOnly }` (или два флага + явный приоритет).
- **Presentation**: только отображение кнопок и текстов; выбор стратегии не в виджетах.
- **DI**: фабрика/реестр, регистрирующий **разные реализации** портов (`IAuthGateway`, `ISyncRemoteExecutor`, при необходимости `ITokenExchange`) в зависимости от стратегии.

## 2. Стратегия A: Firebase + GMS

### 2.1. Вход

- Google Sign-In, Apple (где доступно), анонимный Firebase Auth.
- HUAWEI ID **опционально**: можно оставить только в стратегии B **или** оставить и здесь, если GMS есть (единый Firebase-пользователь через custom token) — продуктовое решение.

### 2.2. Облако

- Firestore / Realtime Database / Storage / Callable через стандартные FlutterFire пакеты без HTTP-обходов (кроме уже принятых исключений).

### 2.3. Синхронизация задач

- Текущий `FirebaseTaskSyncExecutor` и очередь синхронизации без изменений по смыслу.

---

## 3. Стратегия B: Huawei (без полноценного GMS)

### 3.1. Вход

- **HUAWEI ID** через HMS Account Kit (как сейчас).
- Обмен `id_token` на сессию:
  - **Вариант B1 (минимальный)**: по-прежнему **Firebase Auth custom token** через `signInWithHuawei` (сервер проверяет JWT Huawei), вызов функции — **HTTP POST** на Gen1 URL (уже в коде при `not-found` от нативного SDK), чтобы не зависеть от GMS.
  - **Вариант B2 (полный отказ от Firebase на клиенте)**: свой бэкенд (REST), выдача **своих** access/refresh токенов; Firebase на клиенте не используется. Требует отдельного API, хранения пользователей, политики безопасности.

Рекомендация для поэтапного внедрения: **сначала B1**, затем при необходимости **B2**.

### 3.2. Облако и синхронизация при B1

- Auth остаётся Firebase; **данные** — как сейчас, но все вызовы, которые на Huawei без GMS ломаются, должны иметь **тот же класс обходов**, что и для Functions (прямой HTTPS к REST API Firebase **не** рекомендуется без тщательной оценки — проще точечно заменять только проблемные SDK).

### 3.3. Облако и синхронизация при B2

- Отдельный `ISyncRemoteExecutor` (REST/WebSocket), маппинг сущностей в те же domain-модели.
- Миграция данных и привязка `uid` Huawei ↔ пользователь на бэкенде.

## 4. Архитектура (SOLID, слои)

1. **Domain**
   - `IAuthSessionGateway` / разделение «кто выдал сессию» (Firebase vs Huawei-only).
   - Контракты без импорта Flutter/HMS/Firebase.

2. **Data**
   - `FirebaseAuthGatewayImpl`, `HuaweiHmsAccountKitGatewayImpl`, `HuaweiFirebaseTokenGatewayImpl` (и при B2 — `HuaweiRestAuthGatewayImpl`).
   - `GmsAvailabilityPort` + Android-реализация.

3. **Presentation**
   - Экран авторизации получает из scope **одну** абстракцию (например, `AuthFlowController` или расширенный `IAuthGateway`), которая внутри делегирует в выбранную стратегию.
   - Кнопки: показывать Google только если стратегия Firebase+GMS; HUAWEI — если стратегия Huawei или гибридное правило продукта.

4. **Конфигурация на старте**
   - После `Firebase.initializeApp` и проверки GMS/HMS — выставить `AuthBackendStrategy` и зарегистрировать scope **один раз** (не перечитывать при каждом кадре).

## 6. Риски и вопросы

- **Blaze / Cloud Functions**: обмен HUAWEI → custom token всё равно требует задеплоенной функции и конфигурации `huawei.oid_audience`.
- **Один пользователь на двух стратегиях**: custom token с префиксом `huawei_` в `uid` должен совпадать с продуктовой моделью (слияние аккаунтов Google и Huawei — отдельное ТЗ).
- **Устройства не Huawei без GMS** (редкие прошивки): стратегия Huawei не подходит — нужен явный **offline-only** или ограниченный режим.
- **Поддержка**: логировать выбранную стратегию и версии HMS/GMS (в debug — подробно, в release — кратко, без PII).

---

## 7. Критерии готовности

- На устройстве с GMS пользователь проходит сценарий Firebase (Google / аноним / при необходимости HUAWEI).
- На Huawei без GMS пользователь проходит HUAWEI ID и получает рабочую сессию (B1: Firebase custom token через HTTP callable при необходимости).
- В коде нет дублирования ветвлений «Huawei» в каждом экране — только через выбранные реализации портов и стратегию.
