# План: система принятия решений

Как спроектировать так, чтобы реально помогало в жизни (и под кейс с домом / стройкой).

---

## 1. Основа: не задачи, а модель задачи

Каждая задача должна быть не строкой текста, а объектом:

```dart
class Task {
  String id;
  String title;

  int importance;     // 1–5
  int urgency;        // 1–5
  int complexity;     // 1–5 (время/усилия)

  double cost;        // деньги
  List<String> materials;
  bool materialsAvailable;

  List<String> dependencies; // другие задачи

  DateTime? deadline;
}
```

Это уже сильно больше, чем обычный таск-менеджер.

---

## 2. Главная идея — индекс выполнимости (Feasibility Score)

Нужен не просто приоритет, а понимание:

> **что я реально могу сделать прямо сейчас**

### Формула (простая, но рабочая)

```text
Score = (Важность × 2 + Срочность × 2)
        - (Сложность)
        - (Стоимость / бюджетный_коэффициент)
        + бонус за доступные материалы
        - штраф за незакрытые зависимости
```

### Пример логики

- Нет денег → задача падает в списке
- Нет материалов → падает
- Есть зависимости → блокируется
- Простая задача → поднимается

В итоге получается **динамический список «что делать сейчас»**.

---

## 3. Статусы задач (очень важно)

Вместо обычного TODO:

- `blocked_money`
- `blocked_materials`
- `blocked_dependencies`
- `ready`
- `in_progress`
- `done`

Это ключевая фишка приложения.

---

## 4. Зависимости (кейс: туалет и пристройка)

Пример:

```text
Разобрать пристройку
  ↑ зависит от
Построить уличный туалет
```

Пока туалет не готов — задача не появляется в «готовых».

---

## 5. Учёт ресурсов (упрощённо, но эффективно)

### Деньги

- задаётся месячный бюджет;
- задача «активируется», если хватает денег.

### Материалы

- список на складе;
- задача проверяет наличие.

---

## 6. Умный режим (главная ценность)

Приложение должно уметь:

### 6.1. Режим «Что делать сегодня»

Показывает:

- только `ready`;
- сортировка по Score.

### 6.2. Режим «Почему я не могу это сделать?»

Показывает:

- нет денег;
- нет материалов;
- нет зависимости.

Это снижает фрустрацию.

### 6.3. Режим «Разбить задачу»

Если:

- высокая сложность;
- высокая стоимость;

→ предлагается разбить на этапы.

---

## 7. Архитектура (под Flutter)

### Слой данных

- Hive / Isar (локально).

### Логика (use case)

- `CalculateTaskScore`
- `GetAvailableTasks`
- `ResolveDependencies`

### UI

Три экрана (или вкладки):

- **Сегодня** — что делать;
- **Заблокировано** — почему нельзя;
- **Ресурсы** — деньги и материалы.

---

## 8. UX, который сделает приложение полезным

### Не показывать всё сразу

Показывать: **«3 лучшие задачи на сегодня»**.

### Объяснять решения

Например:

> «Эта задача недоступна: не хватает 200€»

### Предлагать альтернативы

> «Вместо этого сделай: выкопать траншею»

## 10. Пример под реальный кейс

**Задача:** септик

- важность: 5
- срочность: 4
- стоимость: высокая

→ статус: `blocked_money`

**Задача:** выкопать траншею

- важность: 4
- срочность: 2
- стоимость: 0

→ статус: `ready`  
→ попадает в топ

---

## 11. Следующие шаги реализации (кратко)

1. Расширить доменную модель задачи (поля + статусы + зависимости).
2. Ввести сущности «бюджет» и «склад материалов» (минимальный MVP).
3. Реализовать расчёт Score и вычисление статуса в domain-слое (без привязки к UI).
4. Добавить use case «готовые задачи на сегодня» и «заблокированные с причиной».
5. Сверстать три режима/экрана поверх существующей навигации и локализации.

Документ можно уточнять по мере появления первых пользовательских сценариев (семья, подрядчики, сезонность работ).
