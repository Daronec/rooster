## Rooster — функциональная спецификация приложения

Документ описывает **полный состав функциональности** приложения Rooster (Task Manager) и ключевые пользовательские сценарии, исходя из текущей реализации в коде и проектной документации в `docs/`.

### 1) Назначение и концепция

Rooster — офлайн‑ориентированный таск‑менеджер с «умным» режимом принятия решений:

- **Задачи** сгруппированы по **спискам**.
- Есть **напоминания** (разовые и регулярные), **вложения**, **теги**, **приоритет**, оценка **стоимости**, **материалы**.
- Есть вкладка **«Решения»**: показывает, что можно делать сегодня и почему часть задач заблокирована (ресурсы/зависимости).
- Данные хранятся локально (Hive) и **синхронизируются** через очередь операций при наличии облака.

### 2) Платформы и навигация

- **Платформы**: Android, iOS, Windows (и др. desktop), возможно Web (часть функций ограничена).
- **Навигация**: `auto_route` (табовая структура на основном экране).
- **Основные вкладки** (MainFlow):
  - **Задачи**
  - **Списки**
  - **Решения**
  - **Профиль**

На mobile используется нижняя навигация; на desktop — оболочка (sidebar).

### 3) Модель данных (основные сущности)

#### 3.1 Задача (`TaskEntity`)

Содержит:

- **Идентификаторы**
  - `id` (UUID)
  - `listId` (принадлежность списку)
  - `parentTaskId` (подзадача)
- **Контент**
  - `title`, `description`
  - `tags`
- **Планирование**
  - `dueAt` / `isAllDay`
  - `startAt`, `endAt`, `durationMinutes`
- **Напоминания**
  - пресеты (`reminderPreset`), произвольная дата (`customReminderAt`)
  - постоянные напоминания: маска дней недели + время
- **Приоритет/оценки**
  - `priority`
  - `importance` (1–5), `complexity` (1–5)
  - `estimatedCost`
- **Материалы**
  - список строк материалов (название/количество/стоимость + связь со складом)
- **Вложения**
  - изображения (локальный путь + опциональный `remoteUrl`)
- **Состояние**
  - `status` (pending/completed/cancelled/archived)
  - `isPinned`
  - `contentRevision`, `updatedAtMillis`, `syncState`
- **Роли задачи / команды (Appwrite Teams)**
  - `ownerUserId`, `ownerNameSnapshot` — владелец, создавший задачу
  - `executorUserId`, `executorTeamId` — исполнитель задачи
  - `observerUserId`, `observerTeamId` — наблюдатель задачи

#### 3.2 Список задач (`TaskListEntity`)

- `id`, `name`, `colorArgb`
- ревизия, время обновления, синк‑состояние (офлайн‑модель)

#### 3.3 Профиль и команды

- Профиль пользователя (имя/фамилия/аватар, зависит от стратегии облака)
- Команды Appwrite (`ProfileTeamCardEntity`) и участники (`ProfileTeamMemberEntity`)

### 4) Фичи приложения

#### 4.1 Задачи (вкладка «Задачи»)

**Назначение**: просмотр всех активных задач, сгруппированных по спискам.

**Поведение**:

- Отображение задач группами по `listId`.
- Внутри группы — секции:
  - **Не выполнено** (pending)
  - **Выполнено** (completed/cancelled)
- Поддержка закрепления (pinned) — отдельный блок сверху.
- Группы сворачиваются/разворачиваются, состояние разворота сохраняется.
- Для задач доступны действия:
  - отметить выполненной/не выполненной
  - закрепить/открепить
  - отменить («не буду делать»)
  - удалить (с подтверждением)
  - открыть редактирование
  - открыть детальный просмотр (если включён в UI)

#### 4.2 Создание/редактирование задачи (экран CreateTask)

**Назначение**: ввод всех параметров задачи, вложений, материалов и т.д.

**Поля/блоки**:

- название, описание
- срок/время (весь день, начало/конец)
- список (обязателен)
- исполнитель (если доступны команды Appwrite и получен список участников)
- наблюдатель (если доступны команды Appwrite и получен список участников)
- владелец отображается при редактировании чужой задачи
- напоминание (пресеты + кастом)
- постоянное напоминание (дни недели + время)
- приоритет, важность, сложность
- теги
- оценочная стоимость
- материалы (строки) + выбор материала со склада
- вложения (изображения)
- подзадачи (в режиме редактирования)
- родительская задача
- история изменений (в режиме редактирования)

**Валидации**:

- заголовок обязателен
- список обязателен
- кастомное напоминание требует даты/времени
- стоимость и количества — числа, неотрицательные

**Автосохранение**:

- в режиме редактирования работает debounce‑автосейв.

#### 4.3 Списки (вкладка «Списки»)

**Назначение**: управление списками задач (категории).

**Функции**:

- создание списка (имя + цвет)
- редактирование существующего списка
- удаление списка (с подтверждением)

#### 4.4 «Решения» (вкладка «Решения»)

**Назначение**: объяснимое ранжирование задач по выполнимости.

**Основные экраны**:

- **Today**: «что делать сегодня» (готовые задачи)
- **Blocked**: «почему не могу сделать» (заблокированные задачи с причинами)
- **Resources**: редактор ресурсов (бюджет, склад материалов)

**Факторы** (на уровне домена):

- важность/сложность
- бюджет и стоимость
- склад материалов
- зависимости задач

#### 4.5 Профиль (вкладка «Профиль»)

**Назначение**: управление пользователем, облаком и командами.

**Функции**:

- отображение статуса входа
- вход/выход (в зависимости от стратегии)
- редактирование имени
- аватар (в зависимости от выбранного бэкенда)
- **команды Appwrite**:
  - просмотр команд и участников
  - создание команды (owner)
  - приглашение участника по email (owner)
  - выход из команды

**Важно**: подтверждение инвайта в команду реализуется через return‑URL, который Appwrite добавляет в письмо (страница `/team-invite`).

#### 4.6 Настройки

**Назначение**: пользовательские настройки UI и поведения.

Функции зависят от реализации (в проектных описаниях и UI):

- режим темы (светлая/тёмная/системная)
- прочие пользовательские параметры (уведомления, звук/вибрация, «о приложении» и т.п.)

#### 4.7 Dev Panel (если включено)

Инструменты разработчика и диагностика (в debug/внутренних сборках).

### 5) Облако и синхронизация

#### 5.1 Общий принцип (offline-first)

- Источник истины на устройстве — **Hive**.
- Любое изменение ставится в **очередь синхронизации** (`ISyncQueue`) как операция.
- При появлении сети `SyncManager` отправляет операции в удалённый executor.

#### 5.2 Appwrite sync (Databases + Storage)

- Исходящая синхронизация: `AppwriteTaskSyncExecutor`
- Входящая синхронизация: pull по коллекциям задач/списков.

#### 5.3 Шаринг задач по ролям

Если у задачи выбран исполнитель или наблюдатель:

- документ задачи в Appwrite получает права владельца для `ownerUserId`
- исполнитель получает права `read/update`
- наблюдатель получает право `read`
- в документ добавляется `sharedWith=[executorUserId, observerUserId]` без пустых значений
- у пользователя pull выбирает задачи:
  - либо где `userId == ownerUserId` (свои)
  - либо где `sharedWith` содержит его `userId` (расшаренные)

### 6) Авторизация и стратегии

В проекте предусмотрены разные стратегии (Appwrite/офлайн и др. ветки). Выбор стратегии делается на старте и влияет на:

- доступные способы входа
- доступность команд Appwrite
- доступность синхронизации

### 7) Локализация и UI‑конвенции

- Все пользовательские строки — через JSON `assets/flutter_i18n/*.json` и обёртки `*Strings` в presentation.
- В экранах используются `AppScaffold`, `DefaultAppBar`/`AppAppBar` (как принято в проекте).

### 8) Известные ограничения (по текущей реализации)

- Расшаренная задача может отображаться у участника в группе **«Неизвестный список»**, если сам список не расшарен/не создан у участника.
- Для Appwrite Databases атрибуты коллекций должны быть заведены в консоли (например `sharedWith` для задач).
